# 虚拟通道分配器（`vc_allocator`）模块代码分析

分析对象：`src/vc_allocator.sv`。本文以现有 RTL 为主线，说明输入 VC 如何申请并占用下游 VC、何时释放，以及接口信号如何回到输入缓冲；没有修改设计 RTL。

## 1. 模块功能与位置

`vc_allocator` 处理的是 **Virtual Channel Allocation（VA，虚拟通道分配）**，而不是每周期选择一个 flit 的交换分配。

当一个输入 VC 收到新包的头 flit、路由计算出目标输出端口后，它必须先获得该目标方向下游路由器的一个空闲 VC，随后该包的全部 flit 才能使用这个下游 VC 发送。这个模块维护“本路由器认为每个下游端口的哪些 VC 仍可分配”的状态，并用 `separable_input_first_allocator` 公平地选择本周期的获批请求。

```text
输入缓冲 VC 发起 vc_request + 给出 out_port
        │
        ▼
vc_allocator 检查目标下游端口是否有空闲 VC
        │ request_cmd
        ▼
separable_input_first_allocator 两级仲裁
        │ grant
        ▼
选择具体下游 VC（vc_new）并给出有效脉冲（vc_valid）
        │
        ▼
输入缓冲记录 downstream_vc，后续 switch allocator 使用它发送 flit
```

## 2. 端口、接口与状态（第 3–14 行）

```systemverilog
module vc_allocator #(
)(
    input rst,
    input clk,
    input [PORT_NUM-1:0][VC_NUM-1:0] idle_downstream_vc_i,
    input_block2vc_allocator.vc_allocator ib_if
);

logic [PORT_NUM-1:0][VC_NUM-1:0] request_cmd;
logic [PORT_NUM-1:0][VC_NUM-1:0] grant;
logic [PORT_NUM-1:0][VC_NUM-1:0] is_available_vc, is_available_vc_next;
```

当前 `PORT_NUM=5`、`VC_NUM=4`，所以后三个矩阵都是“5 个端口 × 每端口 4 个 VC”。在 `is_available_vc[p][v]` 中：

- 第一个下标 `p`：目标**下游输入端口**的编号；它由路由后的 `out_port` 指定；
- 第二个下标 `v`：该下游输入端口的 VC 编号；
- 值为 1：该 VC 可以被新的包占用；值为 0：已分配给尚未释放的包。

`idle_downstream_vc_i[p][v]` 是来自相邻下游路由器的空闲反馈；它为 1 表示该下游端口的 VC 已空闲，可以重新分配。

### `input_block2vc_allocator` 接口的实际方向

接口文件为 `src/input_block2vc_allocator.sv`，其 `vc_allocator` modport 定义为：

```systemverilog
modport vc_allocator (
    output vc_new,
    output vc_valid,
    input vc_request,
    input out_port
);
```

因此从本模块视角：

| 接口信号 | 方向 | 含义 |
| --- | --- | --- |
| `ib_if.vc_request[up_port][up_vc]` | 输入 | 输入缓冲的 VC 请求分配下游 VC。 |
| `ib_if.out_port[up_port][up_vc]` | 输入 | 该输入 VC 已由路由计算得到的目标输出端口。 |
| `ib_if.vc_new[up_port][up_vc]` | 输出 | 分配给该输入 VC 的具体下游 VC 编号。 |
| `ib_if.vc_valid[up_port][up_vc]` | 输出 | 分配结果有效；为 1 时 `vc_new` 才可被输入缓冲接受。 |

## 3. 复用两级仲裁器（第 16–25 行）

```systemverilog
separable_input_first_allocator #(
    .VC_NUM(VC_NUM)
)
separable_input_first_allocator (
    .rst(rst),
    .clk(clk),
    .request_i(request_cmd),
    .out_port_i(ib_if.out_port),
    .grant_o(grant)
);
```

这里没有直接把 `ib_if.vc_request` 接入仲裁器，而是使用过滤后的 `request_cmd`：只有“确实请求”且“目标端口至少还有一个空闲下游 VC”的项才竞争。

仲裁器内部先在每个输入端口的 4 个 VC 间选择一个，再在每个目标输出端口的 5 个输入端口间选择一个。最终：

```text
grant[up_port][up_vc] = 1
```

表示该上游输入 VC 本周期获准占用它所指向下游端口的一个 VC。具体两级仲裁细节见 `file/分离式输入优先仲裁器模块代码分析.md`。

## 4. 时序状态：空闲表的复位和更新（第 32–42 行）

```systemverilog
always_ff@(posedge clk, posedge rst)
begin
    if(rst)
    begin
        is_available_vc <= {PORT_NUM*VC_NUM{1'b1}};
    end
    else
    begin
        is_available_vc <= is_available_vc_next;
    end
end
```

这段是本模块真正的资源所有权状态：

- 复位时，所有下游端口的所有 VC 都被认为空闲（全 1）；
- 正常工作时，在每个时钟上升沿同时提交本周期计算好的分配/释放结果；
- `is_available_vc_next` 是组合值，避免同一个时钟沿出现多个相互覆盖的状态更新。

`vc_valid` 和 `vc_new` 本身是组合输出，但下游 VC 的占用状态会在随后的时钟沿写入寄存器。

## 5. 组合逻辑逐段说明（第 58–106 行）

### 5.1 默认值：保持资源状态，清除本周期输出（第 60–69 行）

```systemverilog
is_available_vc_next = is_available_vc;
for(int up_port = 0; up_port < PORT_NUM; up_port = up_port + 1)
begin
    for(int up_vc = 0; up_vc < VC_NUM; up_vc = up_vc + 1)
    begin
        request_cmd[up_port][up_vc] = 1'b0;
        ib_if.vc_valid[up_port][up_vc] = 1'b0;
        ib_if.vc_new[up_port][up_vc] = {VC_SIZE{1'bx}};
    end
end
```

- 首行默认保持当前空闲表。后面的“分配置 0”和“释放置 1”都在此基础上修改 next-state。
- 所有 `request_cmd` 先置 0，未满足条件的请求不会参加仲裁。
- 所有 `vc_valid` 先置 0，因此只有本周期真正得到 `grant` 的 VC 才会收到有效分配。
- 无效时 `vc_new` 置为 `X`，明确表示该值没有含义；使用方必须用 `vc_valid` 作为使能，不能在 `vc_valid=0` 时使用 `vc_new`。

### 5.2 生成可仲裁请求：请求与资源空闲相与（第 71–80 行）

```systemverilog
if(ib_if.vc_request[up_port][up_vc] &
   |is_available_vc[ib_if.out_port[up_port][up_vc]])
begin
    request_cmd[up_port][up_vc] = 1'b1;
end
```

这等价于：

```text
request_cmd[p][v] = vc_request[p][v]
                    AND (目标 out_port[p][v] 至少有一个 available VC)
```

其中一元归约或 `|is_available_vc[...]` 将该目标端口的 4 个空闲位折叠为一位。例如 `is_available_vc[EAST]=4'b0100` 时结果为 1，仍允许请求进入仲裁；若为 `4'b0000`，即使输入 VC 想发送 HEAD，也不能申请这个已经无 VC 可用的 EAST 端口。

## 6. 获批后选择具体 VC 并占用（第 82–93 行）

```systemverilog
if(grant[up_port][up_vc])
begin
    ib_if.vc_new[up_port][up_vc] =
        assign_downstream_vc(ib_if.out_port[up_port][up_vc]);
    ib_if.vc_valid[up_port][up_vc] = 1'b1;
    is_available_vc_next[ib_if.out_port[up_port][up_vc]]
                         [ib_if.vc_new[up_port][up_vc]] = 1'b0;
end
```

`grant=1` 后依次发生三件事：

1. 以目标端口为参数调用 `assign_downstream_vc`，找出一个具体的空闲编号，写到 `vc_new`；
2. 置 `vc_valid=1`，通知输入缓冲本分配有效；
3. 把同一个 `[目标端口][具体 VC]` 的 `is_available_vc_next` 置 0，确保它会在下一时钟沿变为已占用。

例如输入端口 1 的 VC2 请求 EAST，并且仲裁获胜；若 `is_available_vc[EAST]=4'b0100`，则输出 `vc_new[1][2]=2`、`vc_valid[1][2]=1`，并安排 `is_available_vc_next[EAST][2]=0`。

一个目标端口每周期最多只有一个 `grant`：这是内部两级仲裁器的第二级保证的。因此本循环不会在同周期给同一端口的两个请求分配到同一个旧状态下的 VC。

## 7. 释放逻辑：收到下游空闲反馈后归还资源（第 95–104 行）

```systemverilog
for(int down_port = 0; down_port < PORT_NUM; down_port = down_port + 1)
begin
    for(int down_vc = 0; down_vc < VC_NUM; down_vc = down_vc + 1)
    begin
        if(~is_available_vc[down_port][down_vc] &
           idle_downstream_vc_i[down_port][down_vc])
        begin
            is_available_vc_next[down_port][down_vc] = 1'b1;
        end
    end
end
```

只有满足以下两项时才执行释放：本地表中它原本已被占用（`~is_available_vc`）且下游回报它目前空闲（`idle_downstream_vc_i=1`）。这样避免把从未分配的 VC 当作一次新的释放事件处理。

释放操作写入 `is_available_vc_next`，故在下一时钟沿后该 VC 才重新允许新请求通过第 5.2 节的空闲检查。

## 8. `assign_downstream_vc` 函数：固定低编号优先（第 113–123 行）

```systemverilog
function logic [VC_SIZE-1:0] assign_downstream_vc (input port_t port);
    assign_downstream_vc = {VC_SIZE{1'bx}};
    for(int vc = 0; vc < VC_NUM; vc = vc + 1)
    begin
        if(is_available_vc[port][vc])
        begin
            assign_downstream_vc = vc;
            break;
        end
    end
endfunction
```

函数从 VC0 开始寻找第一个可用 VC，遇到后立即 `break`，所以它是**固定低编号优先**，不是 round-robin 分配。例如可用图为 `4'b1010` 时，VC1 首先可用，函数返回 1。

这里的公平性来源需要区分：

- 哪一个上游请求有资格分配：由内部 `separable_input_first_allocator` 的 round-robin 仲裁保证；
- 目标端口内选择哪一个物理下游 VC：当前函数固定选择编号最小的空闲项，不轮换。

## 9. 与输入缓冲和后续交换分配的衔接

`src/input_block_Xiugai2.sv` 将每个 `input_port` 的 `va_new_vc_i`、`va_valid_i` 分别连接到 `va_if.vc_new[ip]`、`va_if.vc_valid[ip]`。`src/input_port_Xiugai2.sv` 又把它们接到各个 `input_buffer`：

```systemverilog
.vc_new_i(va_new_vc_i[vc]),
.vc_valid_i(va_valid_i[vc]),
```

因此分配结果沿着以下方向传播：

```text
vc_allocator.ib_if.vc_new / vc_valid
  → input_block 的 va_if
  → input_port 的 va_new_vc_i / va_valid_i
  → input_buffer 记录下游 VC 编号
  → input_buffer 输出 sa_downstream_vc_o
  → switch_allocator 用 downstream_vc 与 on_off_i 判断是否可发送
```

对应 `switch_allocator_Xiugai1.sv` 的请求条件：

```systemverilog
ib_if.switch_request[up_port][up_vc] &
on_off_i[ib_if.out_port[up_port][up_vc]]
        [ib_if.downstream_vc[up_port][up_vc]]
```

所以 VA 的分配结果决定数据面后续使用哪个下游 VC；交换分配器只在该已分配 VC 的流控 `on_off_i` 允许时，才让 flit 穿过交叉开关。

## 10. 当前代码的关键注意点

1. **`out_port` 必须有效。** 第 75、88、90 行都用 `ib_if.out_port` 作为数组索引；只有在 `vc_request=1` 时，上游路由计算必须保证它是合法端口枚举，不能为 `X`。

2. **分配和释放在同一时钟沿统一提交。** 组合逻辑先基于旧的 `is_available_vc` 决定请求和具体编号，然后把分配/释放写入 `is_available_vc_next`。这使状态变化同步，但也意味着刚由本周期释放的 VC 不能在同一周期立即参与新分配。

3. **`idle_downstream_vc_i` 是资源释放依据。** 若下游空闲反馈没有正确返回，本模块会一直认为该 VC 已占用，最终阻塞对该方向的新包分配。

4. **层次化仲裁并非全局最大匹配。** 一个输入端口多个 VC 同时请求不同方向时，内部 Input-First 仲裁只让一个 VC 进入第二级；这降低硬件复杂度，但可能放弃某些可让更多端口同时完成的组合。

## 11. 总结

`vc_allocator` 把输入 VC 的逻辑请求转化为对下游 VC 的真实占用：先过滤无资源的方向，再通过两级 round-robin 仲裁选择赢家，固定低编号选出具体目标 VC，用 `vc_valid/vc_new` 把结果送回输入缓冲，并等待 `idle_downstream_vc_i` 反馈后释放该资源。它为后续交换分配提供已绑定的 `downstream_vc`，从而保持一个数据包在传输期间使用一致的下游虚拟通道。
