# 轮询仲裁器（`round_robin_arbiter`）模块代码分析

分析对象：`src/round_robin_arbiter.sv`。以下按源码顺序逐段解释，再结合其在 `separable_input_first_allocator.sv`、`switch_allocator_Xiugai1.sv` 中的实际连接说明控制信号如何影响 flit 传输；本说明没有修改设计 RTL。

## 1. 先看完整代码的职责

`round_robin_arbiter` 为多个请求者竞争同一共享资源提供**单周期组合授权**和**跨周期轮询公平性**。

- 同一时刻可以有多个 `requests_i` 置位；模块最多只置位一个 `grants_o` bit。
- 仲裁从当前优先级指针 `highest_priority` 开始，按循环递增顺序查找第一个有效请求。
- 被授权者的下一个编号成为下一周期扫描的起点，因此持续竞争时不会一直偏向低编号请求者。
- 无请求时不授权，优先级指针保持不变。

本工程当前用法有两类：`AGENTS_NUM=VC_NUM=4`（同一输入端口的 4 个 VC 竞争）以及 `AGENTS_NUM=PORT_NUM=5`（5 个输入端口竞争同一输出端口）。

## 2. 按 `round_robin_arbiter.sv` 源码逐段讲解

### 2.1 参数、端口和指针（第 1–12 行）

```systemverilog
module round_robin_arbiter #(
    parameter AGENTS_NUM = 4
)(
    input rst,
    input clk,
    input [AGENTS_NUM-1:0] requests_i,
    output logic [AGENTS_NUM-1:0] grants_o
);

localparam [31:0] AGENTS_PTR_SIZE = $clog2(AGENTS_NUM);
logic [AGENTS_PTR_SIZE-1:0] highest_priority, highest_priority_next;
```

- `AGENTS_NUM` 是仲裁对象数。例如 `AGENTS_NUM=4` 时，`requests_i[3:0]` 分别代表 4 个 VC；`AGENTS_NUM=5` 时代表 5 个输入端口。
- `requests_i` 是仲裁器唯一的竞争输入；它不携带 flit、目的地址或 VC 内容，只表示“该编号请求者需要共享资源”。
- `grants_o` 是 one-hot 授权结果。如 `4'b0100` 表示编号 2 获选。
- `$clog2(AGENTS_NUM)` 计算保存编号需要的位数。当前工程中 VC 仲裁器为 4，所以指针 2 bit；端口仲裁器为 5，所以指针 3 bit。
- `highest_priority` 是寄存器，保存“下一次从哪个编号开始找”；`highest_priority_next` 是组合逻辑计算出的下一状态。

### 2.2 时钟控制：只保存轮询起点（第 20–30 行）

```systemverilog
always_ff@(posedge clk, posedge rst)
begin
    if(rst)
    begin
        highest_priority <= 0;
    end
    else
    begin
        highest_priority <= highest_priority_next;
    end
end
```

这里没有把 `grants_o` 寄存起来，时钟过程仅更新轮询指针：

- `rst=1`：异步将起点设为请求者 0，因此复位后的首次仲裁优先检查编号 0。
- 每个 `clk` 上升沿：把本周期组合逻辑得出的 `highest_priority_next` 存入 `highest_priority`。
- 所以 `requests_i → grants_o` 是组合路径；“下一次谁优先”才是时序状态。

### 2.3 默认值：无请求时不改变状态（第 41–44 行）

```systemverilog
always_comb
begin
    grants_o = {AGENTS_NUM{1'b0}};
    highest_priority_next = highest_priority;
```

两行默认赋值有两个作用：

1. 先把所有授权清零，因此若下面没有找到请求者，输出自然为全 0；
2. 先令下一指针等于当前指针，因此若没有请求，下一时钟沿不会改变轮询顺序。

这也保证 `always_comb` 中所有输出都有赋值，不会在这里推导锁存器。

### 2.4 循环扫描：从当前起点绕一圈（第 45–47 行）

```systemverilog
for(int i = 0; i < AGENTS_NUM; i = i + 1)
begin
    if(requests_i[(highest_priority + i) % AGENTS_NUM])
```

`i` 不是请求者编号，而是相对当前优先级起点的偏移量。实际被检查的编号是：

```text
candidate = (highest_priority + i) % AGENTS_NUM
```

`% AGENTS_NUM` 是回绕运算：例如 4 个请求者且 `highest_priority=3` 时，检查顺序是 `3 → 0 → 1 → 2`，而不是越界。循环最多检查 `AGENTS_NUM` 次，故所有请求者都恰好检查一次。

### 2.5 找到第一个请求者后的动作（第 48–51 行）

```systemverilog
begin
    grants_o[(highest_priority + i) % AGENTS_NUM] = 1'b1;
    highest_priority_next = (highest_priority + i + 1) % AGENTS_NUM;
    break;
end
```

这三行只有在第 47 行的 `if` 找到**第一个有效请求**时才执行。为了读起来更清楚，先把重复出现的索引表达式取一个逻辑名称：

```text
candidate = (highest_priority + i) % AGENTS_NUM
```

代码等价于：

```text
grants_o[candidate]       = 1;                 // 本周期授权 candidate
highest_priority_next     = (candidate + 1) % AGENTS_NUM;
break;                                         // 不再检查后续请求者
```

三行分别做的是：

1. **第 49 行，发出当前周期的授权。** `grants_o[candidate]=1`，表示候选者可以使用共享资源。因为组合块开头已经把整个 `grants_o` 置为 0，所以它是 one-hot 输出。例如 `candidate=3`、共 4 个请求者时，输出是 `grants_o=4'b1000`。
2. **第 50 行，预先安排下一周期的公平起点。** 获胜者不是下一周期仍然最高优先级，而是把“获胜者后一个编号”设为下次第一个检查对象。这样持续请求者每获胜一次，就会主动让出优先位置。
3. **第 51 行，结束本次扫描。** 后面即使还有请求也不再授权，保证一个仲裁器在一个周期只选一人。

### 用一个完整例子逐步代入

设：

```text
AGENTS_NUM        = 4          // 合法编号为 0、1、2、3
highest_priority  = 2          // 本周期先从编号 2 开始
requests_i        = 4'b1011    // bit3=1、bit2=0、bit1=1、bit0=1
```

注意向量 `4'b1011` 从左至右是 bit3、bit2、bit1、bit0，所以请求者 0、1、3 有请求，请求者 2 没有请求。

循环的实际执行过程如下：

| 循环次数 | `i` | 代入后的 `candidate=(2+i)%4` | 检查的请求 | 是否进入第 48 行 | 结果 |
| --- | --- | --- | --- | --- | --- |
| 第 1 次 | 0 | `(2+0)%4 = 2` | `requests_i[2]=0` | 否 | 不修改输出，继续循环。 |
| 第 2 次 | 1 | `(2+1)%4 = 3` | `requests_i[3]=1` | 是 | 找到第一个有效请求，执行第 49–51 行。 |

在第 2 次中，将每一行完全代入：

```systemverilog
// i=1, highest_priority=2, AGENTS_NUM=4
grants_o[(2 + 1) % 4] = 1'b1;       // grants_o[3] = 1
highest_priority_next = (2 + 1 + 1) % 4;
                                         // highest_priority_next = 0
break;                                  // 不再检查 0、1
```

因此，**本周期立即得到** `grants_o=4'b1000`，即请求者 3 获胜；而 `highest_priority` 这个寄存器此刻仍然是 2。等到下一个 `posedge clk`，第 28 行的非阻塞赋值才会把它更新为 0：

```text
当前组合周期：highest_priority=2，grants_o[3]=1，highest_priority_next=0
下一个 clk 上升沿后：highest_priority=0
```

### 为什么要写“获胜者 + 1”

假设请求向量在之后的周期保持 `4'b1011` 不变，下面展示连续时钟周期的行为。表中“起点”是该周期开始时寄存器 `highest_priority` 的值。

| 周期 | 起点 | 扫描顺序 | 首个有请求者 | `grants_o` | 为下一周期保存的起点 |
| --- | --- | --- | --- | --- | --- |
| C0 | 2 | `2 → 3 → 0 → 1` | 3 | `4'b1000` | 0 |
| C1 | 0 | `0 → 1 → 2 → 3` | 0 | `4'b0001` | 1 |
| C2 | 1 | `1 → 2 → 3 → 0` | 1 | `4'b0010` | 2 |
| C3 | 2 | `2 → 3 → 0 → 1` | 3 | `4'b1000` | 0 |

请求者 2 没有请求，所以它只会被检查而不会获胜；持续请求的 0、1、3 则按 `3 → 0 → 1 → 3 ...` 轮流获得资源。若第 50 行不加 `+1`，指针会继续指向刚获胜的请求者 3；只要 3 持续请求，它就会再次被优先检查并可能长期占用资源，轮询公平性就失效。

### `break` 为什么必须存在

以 C0 为例，若删掉 `break`：请求者 3 被置位后，循环仍会继续检查 0、1；它们也有请求，因此会继续置位 `grants_o[0]` 和 `grants_o[1]`。最终会产生多位授权 `4'b1011`，多个请求者会同时认为自己能使用同一资源。现有 `break` 在授权 3 后立刻退出循环，最终只保留 `4'b1000`。

## 3. 端口与内部状态速查

| 信号 | 位宽/类型 | 方向 | 含义 |
| --- | --- | --- | --- |
| `rst` | 1 bit | 输入 | 高有效异步复位；复位时优先级指针回到 0。 |
| `clk` | 1 bit | 输入 | 指针状态更新时钟。 |
| `requests_i` | `AGENTS_NUM` bit | 输入 | 请求向量；`requests_i[k]=1` 表示第 `k` 个请求者申请资源。 |
| `grants_o` | `AGENTS_NUM` bit | 输出 | 授权向量；零或 one-hot。`grants_o[k]=1` 表示第 `k` 个请求者本周期获选。 |
| `highest_priority` | `$clog2(AGENTS_NUM)` bit | 内部寄存器 | 本次扫描的起始请求者编号。 |
| `highest_priority_next` | 同上 | 内部组合信号 | 下一个时钟周期要保存的扫描起点。 |

`highest_priority` 的名称可理解为“当前最高优先级的起始编号”，不是固定优先级；真正优先级顺序会随时钟轮换。

## 4. 仲裁和控制时序

### 4.1 复位与状态寄存

```systemverilog
always_ff @(posedge clk, posedge rst)
```

当 `rst=1` 时，不等待时钟上升沿，立即将 `highest_priority` 清为 0；复位解除后，每个 `clk` 上升沿把组合逻辑生成的 `highest_priority_next` 写入该寄存器。

因此，`grants_o` 本身没有寄存器：请求改变、指针稳定后，授权会经组合逻辑立即更新；公平性状态只在时钟沿更新。

### 4.2 组合扫描与授权

组合块先执行以下默认赋值：

```systemverilog
grants_o = {AGENTS_NUM{1'b0}};
highest_priority_next = highest_priority;
```

随后令 `i` 从 0 扫描到 `AGENTS_NUM-1`，检查循环编号：

```text
candidate = (highest_priority + i) % AGENTS_NUM
```

第一个 `requests_i[candidate] == 1` 的候选者获选：

```text
grants_o[candidate]          = 1
highest_priority_next        = (candidate + 1) % AGENTS_NUM
停止继续扫描（break）
```

例如 `AGENTS_NUM=4`、当前 `highest_priority=2`，且请求为 `4'b1011`（请求者 0、1、3 有效）时，扫描次序是 `2 → 3 → 0 → 1`；请求者 2 无请求，请求者 3 首先有效，故输出 `grants_o=4'b1000`，下一周期起点变为 0。

若所有请求均为 0，循环中没有命中项，输出保持全 0，指针也保持原值。

## 5. 结合 `separable_input_first_allocator.sv` 的两级连接

该模块不是直接连接 flit 数据，而是只传递“谁可以使用资源”的控制信号。实际 flit 由输入缓冲、交叉开关等模块沿已授权路径传输。

```text
输入缓冲的请求/路由信息
        │
        ▼
switch_allocator 或 vc_allocator 生成 request_cmd[输入端口][VC]
        │
        ▼
separable_input_first_allocator
  第一层：每个输入端口 1 个 round_robin_arbiter（VC 间选择）
        │ vc_grant
        ▼
  根据获选 VC 的 out_port_i 形成 out_request[输出端口][输入端口]
        │
  第二层：每个输出端口 1 个 round_robin_arbiter（输入端口间选择）
        │ ip_grant
        ▼
  grant_o[输入端口][VC]（只有同时赢得两层的 VC 为 1）
        │
        ├─ switch_allocator：选择输入 VC、交叉开关输入端口并置 valid_flit_o
        └─ vc_allocator：分配下游 VC，并更新其可用状态
```

### 5.1 第一层实例：输入优先（Input-First）VC 仲裁

文件：`src/separable_input_first_allocator.sv`。

源码第 25–35 行的 `generate for` 会对每个 `in_arb`（输入端口）生成一个仲裁器：

```systemverilog
.requests_i(request_i[in_arb])
.grants_o(vc_grant[in_arb])
```

其中 `request_i[in_arb]` 是一个输入端口的全部 VC 请求，`vc_grant[in_arb]` 是该端口内的一位 VC 胜者。也就是说，在一个输入端口内，多个虚拟通道先竞争；每个输入端口第一层最多保留一个 VC。获选 VC 的 `out_port_i[in_port][in_vc]` 决定该输入端口随后向哪个输出端口发出第二层请求。

对应源码第 80–83 行：

```systemverilog
if(vc_grant[in_port][in_vc])
begin
    out_request[out_port_i[in_port][in_vc]][in_port] = 1'b1;
    break;
end
```

这段代码把第一层的 `vc_grant` 转换成第二层的 `out_request`。例如输入端口 1 的 VC2 获选，且 `out_port_i[1][2]=EAST`，则产生 `out_request[EAST][1]=1`：即“输入端口 1 请求 EAST 输出”。

### 5.2 第二层实例：输出端口仲裁

源码第 46–56 行为每个 `out_arb`（输出端口）再实例化一个仲裁器：

```systemverilog
.requests_i(out_request[out_arb])
.grants_o(ip_grant[out_arb])
```

`out_request[out_port][in_port]=1` 的含义是：该输入端口在第一层获胜的 VC，希望使用这个输出端口。第二层从这些输入端口中选择一个。

最后，源码第 94–97 行将两层结果相与：

```systemverilog
if(ip_grant[out_port][in_port] & vc_grant[in_port][in_vc])
begin
    grant_o[in_port][in_vc] = 1'b1;
    break;
end
```

所以最终 `grant_o[in_port][in_vc]` 只有在“该 VC 赢第一层”且“它所在的输入端口赢第二层”时为 1。

这种分离式输入优先仲裁避免构造一个很大的全连接仲裁器，代价是每个输入端口每周期只能向一个输出端口提出有效竞争。

## 6. 结合 `switch_allocator_Xiugai1.sv` 看授权如何控制 flit

### 在 `switch_allocator` 中

`switch_allocator` 先根据输入缓冲的 `switch_request`、路由计算得到的 `out_port` 和下游 `on_off_i` 流控状态生成 `request_cmd`。只有目标下游 VC 可接收时，VC 才会进入仲裁。

最终 `grant[up_port][up_vc]` 有效后，它控制三件事：

1. `ib_if.vc_sel[up_port] = up_vc`：通知输入块从哪个 VC 取当前 flit；
2. `xbar_if.input_vc_sel[target_out_port] = up_port`：通知交叉开关该输出应选择哪个输入端口；
3. `valid_flit_o[target_out_port] = 1`：声明该输出端口本周期有有效 flit。

因此，仲裁授权是“输入 VC → 交叉开关指定输出”的控制许可，flit 内容不经过仲裁器本身。

### 在 `vc_allocator` 中

VC 分配器使用相同的两级仲裁结构，但其资源是下游虚拟通道。`grant` 有效后，模块从对应输出端口的空闲 VC 中选择 `vc_new`，置 `vc_valid=1`，并在下一个时钟周期将该下游 VC 标记为不可再分配，直至收到 `idle_downstream_vc_i` 指示其释放。

## 7. 当前实现的关键语义与注意点

1. **指针在“本仲裁器看到任意请求”时前移。** 当前模块没有 `accept`、`ready` 或“最终传输成功”输入。因此第一层 VC 仲裁器即使其获选 VC 随后在第二层输给其他输入端口，仍会在下一个时钟沿把优先级转到该 VC 的下一个编号。该行为是当前 RTL 的既定语义，公平性基于仲裁尝试，而不是基于最终完成的资源授予。

2. **输出是 one-hot 或全零。** `break` 保证一次组合扫描只会设置一个授权 bit；使用方可以把 `grants_o` 当作选择信号，但必须保持请求、路由和流控输入在当前周期满足其时序约束。

3. **异步复位，组合授权。** `rst` 拉高时指针立即复位；`grants_o` 仍由组合请求与复位后的指针决定。上层通常应在复位期间禁止有效数据传输，避免把组合授权误当作一次真实传输。

4. **参数范围。** 当前参数值 4 和 5 均正常：指针宽度分别为 2 和 3 bit，候选编号经 `% AGENTS_NUM` 限制在合法范围。若未来支持 `AGENTS_NUM=1`，`$clog2(1)=0` 会产生零宽度指针风险，应单独保护参数宽度。

5. **综合代价。** 表达式中的 `% AGENTS_NUM` 用于环形索引。现有小规模常数（4/5）可综合；若将请求者数扩展很大，建议评估综合后的组合路径和资源，并可改用显式回绕比较以便更容易控制时序。

## 8. 总结

该模块以一个可轮换的起始指针实现基本 round-robin 策略：组合逻辑立即选出循环顺序中第一个请求者，时钟逻辑把下一次起点移动到该请求者之后。它在 NoC 中被两级复用，先选择输入端口内的 VC，再选择争用同一输出端口的输入端口；最终授权再驱动输入缓冲选择、交叉开关选择、有效标志或下游 VC 占用控制。
